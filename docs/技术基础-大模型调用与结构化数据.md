## 一、调用大模型，本质上就是发一个 HTTP 请求

你平时说"调用 AI"，在代码层面没有任何魔法，就是**发一个 POST 请求**：

```python
httpx.post(
    "https://www.dmxapi.cn/v1/chat/completions",
    headers={"Authorization": "Bearer <你的key>"},
    json={...}          # ← 请求体
)
```

请求体（body）只有四个关键字段：

```json
{
  "model": "deepseek-v4-flash-guan",       // 用哪个模型
  "messages": [                             // 对话内容，是个数组
    {"role": "system", "content": "你是一个记账助手…"},   // 系统提示词：设定身份和规则
    {"role": "user",   "content": "今天买了300块面粉"}    // 用户说的话
  ],
  "temperature": 0,                         // 随机性，0 = 尽量固定输出
  "response_format": {"type": "json_object"} // 可选：要求它输出 JSON
}
```

**`messages` 数组是核心概念**：模型本身是无状态的，它记不住上一轮说了什么。
所谓"多轮对话"，其实是**你把之前的对话全部拼回数组里再发一次**。
（本项目的 `flows/query.py`、`flows/chat.py` 都只发单轮，所以没有多轮记忆能力——
这是设计取舍，也是后面可以改进的点。）

对应的代码：`backend/app/llm/client.py:43-82`

## 二、模型返回的是什么？（这里是最容易误解的地方）

返回的是一坨 JSON，但**里面的内容才关键**。本项目实测的真实返回：

```json
{
  "id": "1ff5bc2d-...",
  "model": "deepseek-flash",
  "choices": [
    {
      "message": {
        "role": "assistant",
        "content": "{\"date\":\"今天\",\"item\":\"面粉\",\"amount\":300,\"currency\":\"CNY\"}",
        "reasoning_content": "我们需要回答用户。用户说\"今天买了300块面粉\"。需要只输出 JSON...
                              但\"300块面粉\"有歧义：300元买面粉，还是买了300块（块状）面粉？
                              ...可输出：{\"日期\":\"今天\",\"商品\":\"面粉\",\"金额\":300,\"单位\":\"元\"}
                              ...最好用英文键？"
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {"prompt_tokens": 43, "completion_tokens": 358, "reasoning_tokens": 339}
}
```

### 三个必须看懂的细节

**① `content` 是一段「字符串」，不是「数据对象」**

注意里面的 `\"` ——这是转义符。意思是：`content` 的值本身是一串**文本**，
这串文本**恰好长得像 JSON 而已**。

所以代码里必须多一步：

```python
content = data["choices"][0]["message"]["content"]   # 得到 str
obj = json.loads(content)                             # 字符串 → Python 字典
```

对应 `llm/client.py:84-93` 的 `extract()`，以及 `extract_json()` 处理模型可能
加上的解释文字和 ```json 围栏。

**② 字段名完全没有保证**

我这次提示词写得很随意（只说"输出 JSON"），模型给的字段是 `date/item/amount/currency`；
而它自己在思考里还盘算过 `日期/商品/金额/单位` 这套中文键名。

**如果你直接 `obj["category"]`，就会 KeyError 崩溃。**

**③ 它自己都在犹豫，而且会算错**

看 `reasoning_content`（推理过程）——模型在纠结"'300块'是钱还是数量"，
并且把"今天"**原样抄进字段，没有换算成 `2026-10-11`**。

> 📌 这不是模型"笨"，而是它的本质决定的：**它是个文字接龙引擎，做的是"最可能的下一个词"，
> 不是"精确计算和格式转换"**。凡是要求精确、可复现的事情，都不该指望它。

这就是为什么本项目要**把今天的日期注入提示词**（`prompts.py:160-166`），
并且另写一套**确定性的中文日期解析器**（`validator.py:185-247`）作为兜底。

## 三、三道闸：把"字符串"变成"可信数据"

问题的本质：**模型输出的是"文本"，而程序需要的是"有类型、有约束的数据"。**
中间要做三次收紧，从软到硬：

### 闸门 1：提示词（软约束，靠模型自觉）

```python
system_prompt = """你是中文记账助手…
输出严格 JSON，不要任何多余文字。结构如下：
{"intent": "record | query | correct | setup | smalltalk",
 "transaction": {"type": "expense | income | transfer", "amount": 数字(元), ...}}
…
用户: 今天买了300块的面粉
助手: {"intent":"record","transaction":{"type":"expense","amount":300,...}}   ← few-shot 示例
"""
```
（`llm/prompts.py`）

- **few-shot** = 在提示词里给几个"输入 → 期望输出"的例子。
  这是提升准确率最便宜的手段，比写一堆规则描述有效得多。
- 特点：**只是"请求"，不是"强制"**。模型可能不听。所以还需要下面两层。

### 闸门 2：`response_format`（API 级约束，只管格式）

```python
payload["response_format"] = {"type": "json_object"}
```
（`llm/client.py:59-60`）

这是**服务端层面的强制**：模型被约束成必须输出合法 JSON。
但它**只管"是不是合法 JSON"**——字段叫什么、类型对不对，它一概不管。
模型完全可以返回 `{"随便": "什么"}`，也是合法 JSON。

> 这也是一种"API 调用手段"，你猜的方向是对的。它属于**调用参数**，
> 和 `temperature`、`max_tokens` 是一类东西。

### 闸门 3：Pydantic（代码级校验，管内容）

这才真正管住"字段对不对"。先用类型注解定义一个"数据形状"：

```python
class TransactionDraft(BaseModel):
    type: Literal["expense", "income", "transfer"] = "expense"
    amount: Optional[Decimal] = None
    date: Optional[str] = None
    category: Optional[str] = None
    confidence: Literal["high", "medium", "low"] = "medium"
```
（`llm/schemas.py`）

然后一行代码完成校验：

```python
return Extraction.model_validate(data)     # 不合格就抛异常
```
（`llm/client.py:93`）

把这里的三个写法讲清楚（这就是你说"没懂"的地方）：

| 写法 | 含义 | 作用 |
|---|---|---|
| `Literal["expense","income","transfer"]` | **枚举**：值只能是这三个之一 | 模型返回 `"type": "买东西"` → 直接抛异常，不会带脏值往下走 |
| `Optional[str]` | 可以是字符串，**也可以是 None** | 明确允许"这个信息用户没说" |
| `Decimal` | 高精度小数（不是 float） | 钱的场景不能用 float，`0.1+0.2` 会等于 `0.30000000000000004` |
| `= "expense"` | 默认值 | 模型没给这个字段时用什么 |

**一句话总结 Pydantic 的价值**：

> 它把"AI 只能从这几个值里选"这件事，**从提示词的软请求变成了代码的硬约束**。
> 提示词是"请你别乱来"，Pydantic 是"你敢乱来程序就报错"。

### 三道闸的完整链路

```
模型输出字符串
   ↓ json.loads()         把字符串变字典
   ↓ Pydantic 校验         字段名/类型/枚举/默认值
   ↓ 领域规则兜底          中文金额、日期用确定性代码重算
   ↓ 人工确认              用户看一眼
   ↓ 事务落账              写失败就回滚
```

**关键认知：这些"技术性的约束"不是 API 调用的手段，而是"防御层级"。**
`response_format` 和 `Pydantic` 确实是 API/代码层面的技术手段，
但它们的意义是**在"AI 不可信"这个前提下，把风险一层层削掉**。

## 四、第二种范式：Function Calling / Tool Calling（EasyAccounts 用的）

这是本次 `Study/EasyAccounts-main` 里最值得学的一点。

### 4.1 原理

上一节的做法叫**抽取式**：让 AI 吐出结构化数据，**然后由你的代码决定怎么做**。

还有另一条路，叫**工具调用式**：你把一批"函数"介绍给模型，模型不再吐数据，
而是**直接说"我要调用哪个函数、参数是什么"**，你的代码执行那个函数。

```python
tools = [{
    "type": "function",
    "function": {
        "name": "add_flow",
        "description": "添加一条流水记录",
        "parameters": {
            "type": "object",
            "properties": {
                "amount": {"type": "number", "description": "金额"},
                "type":   {"type": "string", "enum": ["income", "expense"]},
            },
            "required": ["amount", "type"],
        },
    },
}]
```

模型返回的不再是内容，而是：

```json
"tool_calls": [{"function": {"name": "add_flow", "arguments": "{\"amount\":50,\"type\":\"expense\"}"}}]
```

你的程序解析出这个调用，**去真正执行 `add_flow(50, "expense")`**。

> ⚠️ 注意 `parameters` 里同样有 `enum` 和 `required` ——
> **这就是"受控词表"和"必填字段"写在协议层的样子**。
> 骨架和抽取式是同一套，只是执行方式不同。

### 4.2 EasyAccounts 的做法

从它的文档可以看到（`Study/EasyAccounts-main/AI/README.md`）：

- 内置 **8 个工具**：`accounts`(查账户) / `types`(查分类) / `current_date`(取时间) /
  `year_statistics` / `flows`(流水查询) / `add_flow`(记账) / `update_flow`(改) / `make_excel`(导报表)
- 基于 **Tool Call** 实现，**Agent 框架（koalaq_hub）+ FastMCP**
- 支持 **MCP 协议**（SSE / Streamable-HTTP），能接第三方 AI 工具
- 支持**图片识别**（VL 多模态模型，拍小票自动识别）

它的 AI 会**自动串联多个工具**。文档里的例子：

> 用户问"这个月微信的餐饮支出"，AI 会：
> 1. 先调 `current_date` 拿当前日期
> 2. 再调 `accounts` 拿微信账户 ID
> 3. 然后调 `types` 拿餐饮分类 ID
> 4. 最后调 `flows` 查询具体流水

这叫 **Agent 循环（ReAct 模式）**：模型思考 → 调用工具 → 看结果 → 再思考 → 再调用…
直到能回答用户。**你的项目没有这个循环**，是"一问一答"式的单轮抽取。

### 4.3 MCP 是什么（一句话）

**MCP = 把"你的工具"用一套标准协议暴露出去，让任何支持 MCP 的 AI 客户端都能调用。**

打个比方：以前每个 AI 应用都要自己写一遍"怎么连你的数据库"，
MCP 相当于给工具装了个 **USB-C 标准接口**——
你按标准做一次，Claude Desktop、Cursor、各种 Agent 框架都能直接插上用。

EasyAccounts 做了 MCP，所以它的记账能力**能被别的 AI 工具挂载**，
这是"能力外溢"，也是当前 AI 应用很热的一个方向。

### 4.4 两种范式怎么选

| | **抽取式**（你的项目） | **工具调用式**（EasyAccounts） |
|---|---|---|
| AI 输出 | 结构化数据（草稿） | 函数调用指令 |
| 谁执行 | 你的代码，**执行前可插入确认** | 你的代码直接执行 |
| 适合场景 | **写入类**、要求可控可审计 | **查询类**、多步骤编排 |
| 多轮能力 | 弱（单轮） | 强（Agent 循环，自动串工具） |
| 用户确认岗门 | **天然易插入** ← 你的优势 | 需要额外设计 |
| 风险 | AI 理解错 → 但被闸门拦住 | AI 乱调工具 → **直接改数据** |
| 实现复杂度 | 低 | 高（要写 Agent 循环、工具协议） |

> 📌 **重要判断**：EasyAccounts 的 `add_flow` 是**AI 直接写库的**，
> 从文档看不出中间有"用户确认"这一环（它的做法是记账后在备注里打 `#AI记账` 标签溯源）。
> 而你的项目是**AI 永远不能直接落账**。
>
> 这不是谁对谁错，而是**面向人群不同**：
> 它面向"个人/家庭用户，自己看得懂账"；你面向"不懂记账的中老年店长，账要能交会计"。
> **你的"确认闸门"在你的场景下是更强的设计**——这一点面试时要能讲出来。

### 4.5 最能打的组合：两者混用

成熟系统通常是**混合**的：

```
查询类意图  → 走工具调用（Agent 自动串 accounts → types → flows，快）
写入类意图  → 走抽取式（出草稿 → 硬校验 → 用户确认 → 落账，稳）
```

这正是你的项目**下一步升级的自然方向**：
保留现在的记账主链路不动，把 `flows/query.py` 那部分模板查询升级成工具调用，
就能拿掉"AI 只能选 6 个预置报表模板"的限制。

## 五、EasyAccounts 值得抄的 6 条经验

一个 5 年、天天在用的开源项目踩过的坑，都写在它的 changelog 里：

| # | 它的经验 | 对应原文 | 你的项目现状 |
|---|---|---|---|
| 1 | **工具描述就是提示词**，描述和业务逻辑对齐后调用准确率才上得来 | "AI 提示词与工具描述与后端业务全面对齐，工具调用准确率提升" | 你的 `prompts.py` few-shot 已经是这个思路 ✅ |
| 2 | **AI 操作失败要显示具体原因**，不能静默卡住 | "AI 操作失败时前端会显示具体原因，不再静默卡住" | 你有兜底文案，但没有把失败原因暴露出来 ⚠️ |
| 3 | **错误要结构化返回** | "AI 错误统一结构化返回，前后端协议更规范" | 你的 `LLMError` + 文案，偏简单 🟡 |
| 4 | **枚举/层级校验不能漏** | "修复 AI 选择一级分类记账导致统计分类找不到明细" | 你的科目用封闭词表 ✅；但 AI 分类偶尔飘到"杂费"⚠️ |
| 5 | **AI 生成的数据要能溯源** | "AI 记账/更新会在备注中默认增加 `#AI记账` 标签" | 你没有标记，无法区分人和 AI 记的 ⚠️ |
| 6 | **多模态能力要检测** | "普通模型上传图片会导致当前对话作废" | 你没做图片，但这是明确的下一步方向 |

**第 5 条特别值得你补**：加一个 `#AI记账` 标签成本极低（Beancount 的 tag 语法本来就支持），
但直接带来"可审计性"——**能回答"这笔是 AI 记的还是人记的"**，这在面试里是个加分点。

## 六、把整条链路串起来（面试可以这样画）

```
用户说："今天买了300块面粉"
      │
      ▼  ① HTTP POST /chat/completions   ← 【API 调用层】
      │     messages=[system(角色+规则+few-shot+词表), user(原话)]
      │     response_format=json_object    ← API 级格式约束
      ▼
   模型返回：content 是【字符串】"{\"date\":\"今天\",...}"
      │        （它可能加解释文字、可能用错字段名、可能算错）
      ▼  ② json.loads() + 剥围栏          ← 【解析层】
      ▼  ③ Pydantic model_validate()      ← 【Schema 层】字段/类型/枚举硬校验
      ▼  ④ 确定性规则重算                   ← 【领域层】中文金额、日期用代码算
      ▼  ⑤ 生成"草稿"存进 SQLite            ← 【草稿层】此时还没落账！
      ▼  ⑥ 用户说"确认"                     ← 【人工闸门】唯一不可绕过的关卡
      ▼  ⑦ 写 → 重载校验 → 失败回滚         ← 【事务层】靠借贷平衡兜底
      ▼
   账本 +0 误差
```

**每一层防的东西都不一样**，这就是"怎么保证正确率"的完整答案。

## 七、速查：这些名词到底是什么

| 名词 | 一句话解释 | 本项目位置 |
|---|---|---|
| **chat/completions** | 大模型最基础的对话接口，一次请求一次回复 | `llm/client.py:52` |
| **messages / role** | 对话数组；system 定规则，user 说话，assistant 是模型 | `llm/client.py:87-90` |
| **temperature** | 随机性。0=尽量固定，记账场景必须用 0 | `llm/client.py:56` |
| **`response_format`** | API 级参数，强制输出合法 JSON（只管格式） | `llm/client.py:60` |
| **few-shot** | 在提示词里给"输入→期望输出"的例子 | `llm/prompts.py:EXAMPLES` |
| **Pydantic** | Python 数据校验库，定义"数据该长什么样" | `llm/schemas.py` |
| **`Literal[...]`** | 枚举类型，值只能从列出的里面选 | `schemas.py:10` |
| **`Optional[X]`** | 可以是 X，也可以是 None | `schemas.py:11` |
| **`Decimal`** | 高精度小数，钱的场景不能用 float | `schemas.py:12` |
| **`model_validate`** | 用模型定义去校验一份数据，不合格就抛异常 | `client.py:93` |
| **Function Calling / Tool Call** | 让模型"调用函数"而不是"返回数据" | EasyAccounts 的核心 |
| **Agent 循环** | 模型思考→调工具→看结果→再思考，直到能回答 | EasyAccounts 的自动串联 |
| **MCP** | 把工具用标准协议暴露，任何 AI 客户端都能接 | EasyAccounts 已支持 |
| **VL 模型** | Vision-Language，能看图的多模态模型 | EasyAccounts 的拍小票 |
| **token** | 计费/长度单位，约等于"字/词的碎片" | 上面 `usage` 里的字段 |
