# 开发知识库

> 本文件是项目的「记忆库」：需求来源、设计决策、开发经验、坑、已知限制。
> 快速上手请看根目录 [CLAUDE.md](../CLAUDE.md)。

## 一、需求来源与用户画像

### 用户的原始诉求（整理自多轮对话）

1. **核心矛盾**：专业记账方式对个体户来说太难了，尤其是**上了年纪的小老板/店长**；但专业记账的好处很多（账目可查、收支清晰、能支撑报税和经营决策）。
2. **三层架构**：底层=专业记账（可复用现成的），中间层=好用的 AI（适配 `deepseek-v4-flash`），上层输入=自然语言。
3. **自然语言记账流程要有确认、反馈**：不能 AI 说啥就是啥，必须有确认环节。
4. **必须能看到专业会计表**：虽然用户不会记账，但账本要专业、可查、可交会计。
5. **数据迁入（重要场景）**：很多人之前用别的记账方式（微信账单/支付宝/银行/随手记/Excel/纸笔），**半途使用本程序**，必须能迁入历史数据。
6. **行业拓展接口**：要预留扩展，比如「卷帘门行业」这样的垂直行业模板。
7. **交付形态演进**：先单人/自用验证（不做账号系统、纯文字），跑通后迁移到微信小程序 + 语音。
8. **技术环境**：本地有虚拟环境（`.venv`），配置了代理 7897；API 走 DMXAPI 中转（key 在 `API_data/令牌_模型.txt`）。

### 目标用户画像

- 个体户、夫妻店、早点铺/面铺/杂货店店主，多在 40-70 岁
- 不懂借贷记账，但每天有真实收支（进货、卖货、房租、水电、请人工资、家里拿钱）
- 手机为主，需要**大字体、大按钮、点按钮胜过打字**、语音是远期刚需

## 二、架构设计

```
┌───────────────────────────────────────────────┐
│ 上层：frontend/ 移动端优先 Web（原生 HTML/CSS/JS）│
│  四页：💬对话 📊看账 📥导入 🏁期初（底部导航）   │
├───────────────────────────────────────────────┤
│ 中间层：backend/app/flows/ AI 编排（FastAPI）  │
│  ├─ chat.py    会话状态机（协调分发）           │
│  ├─ record.py  记账：解析→澄清→确认→落账→反馈   │
│  ├─ query.py   查询：NL→报表模板→白话           │
│  └─ correct.py 纠错：定位→确认→改/冲销          │
├───────────────────────────────────────────────┤
│ 底层：backend/app/core/ Beancount 3 专业引擎    │
│  ├─ beancount_engine.py  加载/校验/追加/报表    │
│  ├─ accounts.py          科目表 + 中文别名      │
│  ├─ validator.py         金额/日期硬校验        │
│  ├─ memory.py            SQLite（映射/草稿/会话）│
│  └─ importer.py          历史账单解析与批量落账  │
└───────────────────────────────────────────────┘
```

**核心原则**：AI 只产出「草稿」，永不直接落账 —— 必须过硬校验 + 用户确认。账本本体是 `.bean` 文本文件（可审计、可备份、可交会计），SQLite 只存流程元数据。

## 三、记账状态机（核心）

```
用户说话
  → llm.extract 结构化JSON (intent: record/query/correct/setup/smalltalk + transaction)
  → record.build_draft 硬校验（金额/日期/科目）
     缺金额 → 澄清（一次只问一个，带快捷按钮）
     缺分类 → 用映射记忆/别名/AI 候选兜底
  → 存入 SQLite 草稿，进入 AWAITING_CONFIRM
     用户「确认」→ 落账 → 反馈余额+本月收支
     用户「不对，是480」/「480」→ 改金额 重新确认
     用户「记到银行」→ 改现金侧科目
     用户「取消」→ 作废，不落账
     用户说新指令 → 旧草稿作废（覆盖）
```

**确认态关键词分类**（`flows/base.py` + `chat._classify`）：
- 确认：确认/确定/对的/没错/可以/好/行/ok…
- 取消：取消/算了/不记/别记/不要/撤销…
- 修改：不对/错了/不是/改…/记到/记成/是现金/是银行/走微信/删掉…
- 纯数字或「是480」→ 视为改金额（前提：能解析出金额且与草稿不同）

## 四、专业报表口径（重要，勿改错）

- **科目余额表（试算平衡）**：每账户 借方合计 / 贷方合计 / 期末余额。Beancount 借方=正、贷方=负，全账余额之和恒 0。
- **利润表**：某区间内 Income:* 取反（负余额→正收入）、Expenses:* 取正 → 净利 = 收入 - 支出。
- **资产负债表**：资产=累加余额；负债=负余额取反；权益=负余额取反；**未分配利润 = 累计收入 - 累计支出**（收入费用未结转损益时的简化处理，保证 资产=负债+权益 恒等）。`balance_sheet()` 返回 `balanced` 布尔供前端校验展示。
- **明细账**：`account_ledger()` 逐笔 + 余额累进（`running`）。
- 历史数据安全：导入/期初都先整体追加→`loader` 重载校验→失败整批回滚，绝不半落账。

## 五、历史数据迁移（用户重点场景）

**两条路径，全部走 Beancount 专业校验：**

1. **期初余额**（`/api/opening-balance`）：填现金/银行/存货/应收/应付/借款 → 借方=资产、贷方=负债、差额 → `Equity:OpeningBalances` 平账。中途接手账本的第一步。
2. **历史导入**（`/api/import/preview` + `/api/import/commit`）：
   - 上传微信/支付宝/银行导出的 CSV/Excel（`python-multipart` + `openpyxl`）
   - `importer.detect_columns` 按别名组识别列（日期/金额/收支/分类/对方/备注），**微信「收/支+金额(元)」、支付宝「商品名称+收/支+金额」、银行「收入/支出双列」三种格式都实测通过**
   - `importer.parse_rows` 逐行校验，坏行进 `skipped`（不中断）
   - `llm.map_categories` 批量分类（实测面粉→存货、房租→租金、电费→水电、工资→工资全对，约 5s）
   - 前端逐类核对可改 → 预览前 10 条 → 确认导入
   - **转账识别**：微信「零钱提现」等自己账户互转 → `Assets:Bank ↔ Assets:Cash` 互转，**不误计为收支**

## 六、开发经验与坑（血泪教训）

### Beancount 3（版本 3.2.3）API 与网上教程不一致
1. **`Posting` 没有 `.position`**，金额在 `posting.units`（类型 `Amount`）。遍历 posting 一律先判 `posting.units is None`（padding 行）再取值 `units.number / units.currency`。
2. **格式化条目**：用 `from beancount.api import format_entry`，返回 **str**。`beancount.parser.printer.print_entry` 在 v3 返回 **None**（直接 `"\n".join(...)` 会 `TypeError: expected str instance, NoneType`）——这是最容易踩的坑。
3. **借贷方向**：Beancount 不区分借/贷关键字，用**正负号**表达。资产/费用记正（借方），收入/权益/负债记负（贷方）。`append_transaction` 的 `postings=[(account,'dr'|'cr',正数金额)]` 内部换算：dr→正、cr→负。
4. **校验与回滚**：`loader.load_file()` → errors 非空即不健康。所有写操作（`append_text`/`save_entries`）先备份原文→写文件→重载校验→失败写回原文。**绝不跳过校验。**
5. **重构/改账**：`save_entries` 只保留 `Open` 和 `Transaction`，用 `format_entry` 重建整个文件再校验。

### Windows + 中文
- 控制台打印中文乱码 = GBK 编码问题。跑脚本/命令前加 `PYTHONIOENCODING=utf-8`。文件读写一律 `encoding="utf-8"`。
- Git Bash 里 `taskkill //F //IM python.exe`（双斜杠）杀残留 uvicorn；重启服务前先杀再清 `data/*.db` `ledger.bean`。

### AI（DeepSeek V4 Flash via DMXAPI）
- 走 OpenAI 兼容 `/chat/completions`，支持 `response_format={"type":"json_object"}` 和 FunctionCall（P0 实测）。
- JSON 抽取延迟约 8s、批量分类约 5s —— 前端要展示「正在记账…」，导入要有「正在解析…」提示。
- AI 可能返回多余文字：`extract_json()` 剥 ```json 围栏 + 取首尾 `{}`。再 Pydantic 校验，失败走澄清，绝不崩。
- `prompts.py` 的 few-shot 示例日期用 `{today}` 占位，运行时动态替换（避免模型以为示例是"今天"）。

### 金额/日期解析（validator.py）
- 支持：中文数字（三百五→350、三万五→35000）、单位（万/千/百/块/毛/角/分）、小数（三点五→3.5）、相对日期（今天/昨天/前天/N天前/上周三/上个月/8月5号/2026-8-3）。
- 陷阱：`三百零五`=305（中间有零不省略）；`12块5毛` 用专用正则 `_MONEY_RE` 而不是先剥货币字再拼（会拼成 125.5）；未来日期（8月5号今年未到→自动回退去年）。
- 金额一律正数，`parse_amount("-5")` 返回 5（负号当噪音，不视为负金额）。

## 八、前端要点

- 原生 JS，无框架（验证期；后续迁移小程序只需重写 frontend，API 不变）
- `app.js` 四个页面切换（底部 `#tabbar`），看账页 `loadBooks()` 并行拉利润表/资产负债表/试算平衡，明细账按科目切换
- 导入页：选择文件→`FormData` POST `/api/import/preview`（multipart）→渲染分类核对（`<select>` 可改，改了更新 mapping）→预览→commit
- 大字体（根 `font-size:18px`）、大按钮、快捷回复 chips；`env(safe-area-inset-bottom)` 适配全面屏

## 九、已知限制与下一步

- **限制**：单用户无登录；存货成本结转是「确认时二选一」的简化，无自动成本核算；报表在 MVP 用 Python 聚合（无 bean-query SQL）；草稿超时未自动清理 UI（DB 有过期逻辑）
- **下一步**（按优先级）：
  1. 真实用户试用一周，调 few-shot（`llm/prompts.py`）提升口语识别准确率
  2. **行业拓展接口**（用户明确需求）：卷帘门等垂直行业 → 把科目表+提示词+分类映射做成可配置模板（如 `industries/rollup_shutter.json`），启动时按行业加载
  3. 微信小程序前端（核心已解耦）
  4. 语音输入（老年店长刚需）
  5. 多用户/多租户、草稿箱找回、报表导出 Excel/PDF
