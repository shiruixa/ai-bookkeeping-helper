# 从自然语言到结构化数据：一套可复用的 AI 录入方法论

> 本文把「AI 记账助手」这个项目里**自然语言 → 结构化数据**的完整做法拆开讲透，
> 并抽象成一套能直接搬到「自动设备管理 / 巡检录入 / 工单录入」等场景的通用模式。
> 每一节都标了本项目的源码位置，方便对照。

---

## 〇、一句话说清核心矛盾

> **难点从来不是"让 AI 听懂人话"，而是"AI 一定会错，但数据不能错"。**

任何一个 AI 录入系统都同时在解两个问题，而它们的目标是**冲突**的：

| 维度 | 目标 | 手段 | 能达到的上限 |
|---|---|---|---|
| **识别准确率** | AI 把人话理解对 | 提示词、few-shot、记忆学习 | 永远到不了 100%（口语本身就有歧义） |
| **数据正确性** | 错的绝不进系统 | 确定性校验 + 人工确认 + 事务回滚 | **可以做到接近 100%** |

大部分 demo 只做第一件事，所以一上真实数据就崩。
本项目的全部设计重心在第二件事——**承认 AI 会错，然后让"错"没有机会污染数据**。
这句话是整份文档的主线，也是面试时最该讲的那句。

## 一、整体架构：四道关卡

```
用户随口一句话
   │
   ▼
① 意图理解 + 结构化抽取      ← LLM（唯一不可信的一层）
   │  产出：JSON 草稿
   ▼
② 确定性硬校验              ← 纯 Python 规则（可信）
   │  校验不过 → 澄清 / 拒绝，绝不放行
   ▼
③ 人工确认闸门              ← 用户（可信的最终裁判）
   │  确认 → 放行；修改 → 回炉；取消 → 丢弃
   ▼
④ 事务性落账                ← 写 → 重载校验 → 失败整批回滚
   │
   ▼
结构化、可审计、可导出的数据
```

**关键设计**：LLM 只在 ① 出现，而且它产出的东西叫"**草稿(draft)**"不叫"数据"。
从草稿到数据，中间必须穿过三道确定性关卡。

对照源码：
- ① `backend/app/llm/client.py:extract()` + `llm/prompts.py` + `llm/schemas.py`
- ② `backend/app/core/validator.py` + `flows/record.py:build_draft()`
- ③ `backend/app/flows/chat.py`（状态机）
- ④ `backend/app/core/beancount_engine.py:append_text()`

## 二、关卡①：让 LLM 输出**稳定的结构**，而不是自由文本

### 2.1 三层约束叠加

| 手段 | 做法 | 源码 |
|---|---|---|
| **格式约束** | 走 OpenAI 兼容的 `response_format={"type":"json_object"}` | `llm/client.py:59-60` |
| **结构约束** | Pydantic 模型强校验，字段类型/枚举全部写死 | `llm/schemas.py` |
| **语义约束** | few-shot 示例 + 受控词表（科目表）写进提示词 | `llm/prompts.py:157-197` |

Pydantic 这一层是关键，注意它的写法：

```python
class Extraction(BaseModel):
    intent: Literal["record", "query", "correct", "setup", "smalltalk"]
    transaction: Optional[TransactionDraft] = None
    ...
class TransactionDraft(BaseModel):
    type: Literal["expense", "income", "transfer"] = "expense"
    amount: Optional[Decimal] = None      # 用 Decimal 不用 float，避免金额精度漂移
    confidence: Literal["high", "medium", "low"] = "medium"
```

`Literal` 把"AI 只能从这几个值里选"这件事**从提示词的软约束变成了代码的硬约束**——
AI 返回 `"type": "买东西"` 会直接被 Pydantic 拦下抛异常，进入澄清流程，而不是带着脏值往下走。

### 2.2 解析失败的三级降级

AI 经常不老实输出纯 JSON（加解释、包 markdown 围栏），所以解析要分层：

```python
def extract_json(text: str) -> dict:
    fence = re.search(r"```(?:json)?\s*(\{.*\})\s*```", t, re.S)  # 1) 剥 ```json 围栏
    if fence: t = fence.group(1)
    start, end = t.find("{"), t.rfind("}")                        # 2) 取首尾大括号之间
    return json.loads(t[start:end+1])
```
（`llm/client.py:22-33`）

再往上还有一层：调用失败自动降级重试。有些中转网关不认 `json_object`，返回 400：

```python
if resp.status_code == 400 and json_mode and attempt == 0:
    del payload["response_format"]   # 降级重试一次
    continue
```
（`llm/client.py:69-72`）

### 2.3 few-shot 里的一个细节：动态日期注入

提示词里的示例带相对日期（"昨天"），如果写死字面量，模型会把示例当成真的"昨天"。
所以用 `{today}` / `{yesterday}` 占位，**运行时按当前日期渲染**：

```python
params = {"today": today, "yesterday": (d - timedelta(days=1)).isoformat()}
```
（`llm/prompts.py:160-170`）

> 📌 **可复用要点**：few-shot 里凡是和"当下"相关的值（日期、当前用户、当前库存），
> 都要运行时注入，绝不能写死在提示词里。

### 2.4 意图路由：先分类，再分派

一句话先被分成五类，再走各自的处理器：

| intent | 含义 | 处理器 |
|---|---|---|
| `record` | 记一笔 | `flows/record.py` |
| `query` | 问报表 | `flows/query.py` |
| `correct` | 改/删已记的 | `flows/correct.py` |
| `setup` | 首次建账 | 汇入 `record.py` 的 setup 分支 |
| `smalltalk` | 闲聊/兜底 | `flows/chat.py` |

（`flows/chat.py:_handle_new()`）

**为什么要显式路由**：不同意图需要完全不同的下游处理和安全策略。
"问报表"是只读的，错了没关系；"记一笔"是写入的，必须走全套校验。
把它们混在一个大 prompt 里让 AI 自由发挥，是最常见的翻车方式。

## 三、关卡②：为什么 LLM 之外还要一层确定性校验

### 3.1 核心洞察：**LLM 负责"理解"，规则负责"正确"**

LLM 有两个天生的弱点：

1. **不擅长精确的字面解析**。"三百五"、"12块5毛"、"三点五"、"3万5"——
   模型经常算错，而且这次算对不代表下次算对。
2. **不可复现**。同样的输入，换个上下文就变了（本项目实测：同一批导入，
   "面粉"有时映射到"存货"、有时映射到"杂费"）。

所以凡是**能用确定性代码算出来的东西，就不该交给 LLM**。

### 3.2 中文金额解析器（确定性，纯正则+状态机）

`core/validator.py:42-164` 手写了一个中文数字解析器，覆盖：

| 口语 | 解析结果 | 陷阱 |
|---|---|---|
| 三百五 | 350 | **口语省略**：尾数 × 末位单位/10 |
| 三百零五 | 305 | 中间有"零"则**不**省略 |
| 三万五 | 35000 | 万级 |
| 12块5毛 | 12.5 | **必须先识别货币单位组**，不能先剥"块"再拼（会拼成 125.5） |
| 三点五 | 3.5 | 小数 |
| 5分 | 0.05 | 只有分币单位 |

这些全是**用正则和状态机一行行推出来的**，不经过模型，所以 100% 可复现、可单测
（`tests/test_validator.py` 里 19 个参数化用例，覆盖了上面每个陷阱）。

日期同理（`validator.py:185-247`）：今天/昨天/前天/N天前/上周三/上个月/8月5号，
以及一条领域规则——**"8月5号"在今年还没到就自动理解为去年**。

### 3.3 双轨兜底：AI 给候选，规则给真值

`flows/record.py:build_draft()` 的取值顺序很讲究：

**金额**：优先用 AI 抽的 `amount`；AI 给不出（null/≤0）→ 用规则从原文再解析一次；
两者都拿不到 → **澄清**，一次只问一个问题（"这笔记了多少钱呢？"）。

**科目**：四级兜底链（`_resolve_business`）

```
① 用户确认过的映射记忆（memory.get_mapping）   ← 最可信，是人的意志
② AI 选的科目（且必须在受控词表内）            ← 次可信
③ 口语别名表匹配（accounts.alias_map）         ← 确定性兜底
④ 领域默认值（Expenses:Misc / Income:Sales）   ← 保底，绝不空转
```

**现金侧科目**（`_resolve_code`）同样是链式：科目代码 → 口语词表（微信/支付宝→银行）
→ 别名表 → 中文科目名 → 默认现金。

> 📌 **可复用要点**：**受控词表 + 多级兜底**。
> 永远不要让 AI 自由生成类目名（"你说的这个设备类别"），而是给它一张枚举表让它选；
> 它选不中时，用"用户历史偏好 → 别名词典 → 默认值"逐级兜底，保证**永远有一个合法值**。

### 3.4 澄清优于猜测

拿不到关键信息时，系统的行为是**停下来问**，而不是"猜一个差不多的"：

```python
if amount is None:
    return None   # → 上层进入澄清流程，不落账
```
（`flows/record.py:88-89`，配套 `clarify_amount()`）

这是整个系统里最反直觉、也最重要的选择：
**宁可多问一句，也不要在用户不知情的情况下写错一个数。**

## 四、关卡③：人工确认——把"不可逆写入"变成"可逆草稿"

### 4.1 状态机

`flows/chat.py` 是一个显式状态机，状态存在 SQLite 的 kv 表里：

```
        ┌──────────┐  说一句话   ┌──────────────────┐
        │   idle   │ ──────────▶ │ awaiting_confirm │
        └──────────┘             └──────────────────┘
              ▲                      │    │     │
              │ 确认                  │    │     └──▶ 说新指令 → 旧草稿作废
              └──────────────────────┘    └────────▶ 修改 → 更新草稿，回到等待
```

关键点：**草稿(draft)是持久化的**（`core/memory.py` 的 `drafts` 表，带 `expires_at` 过期时间），
不是存在内存里。所以服务重启、刷新页面，用户回来还能确认。

### 4.2 确认态的自然语言分类

用户不会规规矩矩点按钮，他会说"对"、"行"、"不对，是480"、"记到银行"、"算了"。
所以确认态要先做一次**轻量意图分类**（不调用 LLM，纯关键词，毫秒级）：

| 类别 | 触发词 | 行为 |
|---|---|---|
| cancel | 取消/算了/不记/不要… | 丢弃草稿 |
| edit | 不对/改…/记到/删了/**不行**/不好… | 更新草稿后重新确认 |
| edit（纯数字） | "480" / "是480" | 快速改金额（口语友好） |
| confirm | 确认/好/行/对的/嗯… | 落账 |

> ⚠️ **这里踩过一个真坑**：最初用 `any(w in text for w in CONFIRM_WORDS)` 做子串匹配，
> 而 CONFIRM_WORDS 里有"行"、"好"这两个高频单字 ——
> 结果用户说 **"不行"、"不好"，系统判成"确认"，错账直接落进了账本**。
>
> 修复（`flows/base.py:affirms()`）：
> 1. 把否定词（不行/不好/不可以…）显式收进 EDIT_WORDS，且 **EDIT 先于 CONFIRM 判断**；
> 2. 再加一道保险：确认词只有**不紧跟在否定字（不/别/甭）后面**时才算确认；
> 3. 补了 4+3 个回归测试锁死这个行为（`tests/test_record_flow.py`）。
>
> 📌 **通用教训**：**关键词分类千万不要用单字做子串匹配**。
> 中文里"不X"极易与"X"混淆，必须显式处理否定，并且把这类边界写成回归测试。
> 这个坑在"设备报修录入"里一模一样会出现（"没坏" vs "坏了"）。

### 4.3 修改也要有确认

用户改完金额，系统**不会直接改**，而是重新展示一张新的确认卡片：

```
用户: 不对，是480
助手: 10月11日 面粉 480.00元
         现金 → 存货
      记这笔对吗？【确认】或直接修改
```

（`flows/record.py:to_confirm()` → 重新保存草稿 → 回到 `awaiting_confirm`）

**每一次修改后都要重新确认**，这是防止"改着改着改出个新错误"的关键。
改完就落账是常见设计错误——用户刚说完"改成480"，你落的是 480 还是 300？

## 五、关卡④：落账的正确性——用领域不变式当免费校验器

### 5.1 复式记账的恒等式 = 最强的免费校验

这是本项目最"占便宜"的一点：**会计本身自带一条数学不变式**。

> 每笔交易：借方合计 = 贷方合计（在 Beancount 里表现为"全账余额之和恒为 0"）

于是任何一条"借贷不平"的脏数据，在写进去的瞬间就会被引擎拒绝。
**等于白捡了一个 100% 覆盖的数据完整性约束。**

### 5.2 事务化的写入

```python
original = self.path.read_text(encoding="utf-8")   # 1) 先备份原文
self.path.write_text(original + text + "\n")       # 2) 写
_, errors, _ = self.load()                         # 3) 重载，让引擎校验
if errors:
    self.path.write_text(original)                 # 4) 有错 → 整批回滚
    raise LedgerError(...)
```
（`core/beancount_engine.py:append_text()`，`save_entries()` 同理）

批量导入（80 笔 × 一次写）也走同一条路径：**要么全进，要么全不进**，绝不半落账
（`core/importer.py:commit_rows()`）。

### 5.3 删除用"冲销"不用物理删除

```python
rev = [(p.account, -p.units.number) for p in entry.postings]   # 反向记一笔
```
（`flows/correct.py:111-120`）

**账本永远只增不改**，删一笔 = 追加一笔金额相反的。这样审计线索完整，
任何时候都能回答"这笔账是怎么变成现在这样的"。

> 📌 **可复用要点**：在设备管理里，这就是"**退役/报废用状态变更记录实现，而不是删行**"。

### 5.4 用"专业标准格式"当存储，白捡一整套生态

账本落地是 **Beancount 的纯文本 `.bean`**，而不是自己设计一张表。好处：

- 数据**可读、可 diff、可备份**，用户能直接交给会计
- 复用 Beancount 十余年积累的加载器/校验器/查询引擎
- 出问题时用文本编辑器就能人工介入

📌 **通用思路**：**如果你要解决的问题已经有成熟的标准格式和验证工具，就直接用**，
别自己造一套私有 schema——你不仅省下实现，还白捡了一个经过实战检验的校验器。

## 六、准确率是怎么"长出来"的：人在回路的复利

前面讲的都是"防错"，那**识别率**怎么提升？

### 6.1 映射记忆表：每一次人工确认都是一次训练信号

```python
# 用户确认落账时，顺手记住「口语分类 → 科目」的映射
if category:
    self.memory.save_mapping(category, biz)     # 面粉 -> Assets:Inventory
```
（`flows/record.py:225-231`）

下次用户再说"面粉"，`_resolve_business` 的第一优先级就命中记忆表，
**不再依赖 AI 判断**，直接给出用户自己认可过的科目。

- 冷启动：别名表 + few-shot 兜底
- 用起来之后：记忆表不断增厚，**同一个店主的表达习惯被逐步学会**
- 导入历史账单时也写入记忆表（`importer.py:360-367`）——一份历史数据就是一次批量学习

> 📌 **这是"人在回路(human-in-the-loop)"的复利**：
> 系统不追求一次就全对，而是让**每次人工修正都变成一次永久学习**，
> 于是"用一周"和"用第一天"的准确率不是一个量级。

### 6.2 诚实的一面：识别率还没有被量化

必须承认：本项目**还没有真实用户数据**，所以"识别率"目前只有设计上的把握，
没有测量出来的数字。下一步该做的是收集真实口语的错例，反哺 few-shot。

**面试时这样讲更可信**：
> "数据正确性我在架构上保证了——错的进不来。
> 识别率目前是冷启动水平，我设计了记忆表让它在使用中持续上升，
> 但这个提升曲线还需要真实用户数据才能量出来。"

比硬吹"准确率 95%"可信得多，也显得懂工程。

## 七、正确性保证的完整清单（分层防御总表）

| # | 层 | 手段 | 防住了什么 | 成本 |
|---|---|---|---|---|
| 1 | 提示词 | 受控词表 + few-shot + 动态日期 | 大方向跑偏 | 低 |
| 2 | 输出格式 | `json_object` + `extract_json` 降级 | 输出不是 JSON | 低 |
| 3 | Schema | Pydantic `Literal`/`Decimal` 强校验 | 字段类型/枚举错 | 低 |
| 4 | 业务规则 | 中文金额/日期确定性解析 | AI 算错、不可复现 | 中 |
| 5 | 取值链 | 记忆 > AI > 别名 > 默认 | 分类缺失/乱来 | 低 |
| 6 | 缺信息 | **澄清而不是猜** | 带着空值落账 | 低 |
| 7 | 人工闸门 | 状态机 + 持久化草稿 | 不可逆的错误写入 | 中 |
| 8 | 领域不变式 | 借贷平衡校验 | 数学上不可能的数据 | **极低（白捡）** |
| 9 | 事务 | 写前备份→写→校验→回滚 | 半落账、写坏库 | 低 |
| 10 | 审计 | 冲销不物理删 | 无法追溯 | 低 |
| 11 | 学习 | 映射记忆表 | 同一个错犯两次 | 低 |

**这 11 层里，只有第 1-3 层依赖 LLM，其余 8 层全是确定性代码。**
这个比例本身就是答案：**"怎么保证正确率"的答案是"大部分工作不交给 AI 做"。**

## 八、搬到别处：AI 自动录入的通用骨架（五步法）

不管录入的是记账、设备巡检、工单、还是库存，骨架都一样：

### 第 1 步：定义**受控词表**（最重要的一步）

不要问"AI 能抽出什么"，先问"**我们的领域里，有哪些封闭的取值集合**"。

| 本项目 | 设备管理（举例） |
|---|---|
| 科目表 18 个科目（`core/accounts.py`） | 设备台账编码、故障代码表、位置编码、状态枚举 |
| `Literal["expense","income","transfer"]` | `Literal["报修","巡检","保养","报废"]` |

**词表是 AI 和确定性代码之间的接口契约。** 有了它，AI 的输出才有"能不能对得上"的判据。

### 第 2 步：设计**结构化 Schema**（Pydantic）

每个字段都要问自己：**这个字段的合法值域是什么？能不能用枚举/正则/范围表达？**

```python
class DeviceLog(BaseModel):
    kind: Literal["报修", "巡检", "保养"]
    device_code: Optional[str] = None       # 后面用正则校验格式
    reading: Optional[Decimal] = None       # 读数，注意用 Decimal
    reported_at: Optional[str] = None       # YYYY-MM-DD
    fault_code: Optional[str] = None        # 必须来自故障代码表
    confidence: Literal["high", "medium", "low"] = "medium"
```

### 第 3 步：写**领域校验器**（确定性）

记账用的是"借贷平衡"，你的领域一定有类似的**不变式**：

| 领域 | 可用的免费校验器 |
|---|---|
| 记账 | 借贷平衡、余额非负、科目在词表内 |
| 设备巡检 | 读数在量程内、时间不倒流、巡检项**必填**、设备码存在 |
| 库存 | 数量守恒、批次可追溯 |
| 工单 | 状态转移合法（已报废的不能再报修）|

**先找不变式，再写代码。** 一条好的不变式能替你挡掉一大类脏数据，成本几乎为零。

### 第 4 步：加**人工确认闸门**

- 状态机 + **持久化草稿**（别放内存）
- 确认态支持自然语言修改（"不是这台"、"读数改成 3.5"）
- 每次修改后**重新确认**
- 高危操作（报废、删记录）单独过闸

### 第 5 步：接**反馈学习**

用户每次修正（"不是3号机，是5号机"）都写进映射表：

```
"三号机" -> DEV-003     （用户纠正过一次，下次直接命中）
```

这就是你在这套系统里积累的**私有数据资产**——别人抄不走。

|---|---|---|

## 九、可复用的设计原则（背下来）

1. **LLM 只做"翻译"，不做"裁判"。** 它负责把口语变成结构化候选，正确性由确定性代码裁决。
2. **受控词表优先。** 宁可让 AI 从 20 个枚举里选，也不要让它自由生成类目名。
3. **双轨解析：AI 给候选，规则定真值。** 能用代码算的（数字、日期、编码）绝不交给模型。
4. **缺信息就问，绝不猜着写。** 澄清一次的体验成本，远低于写错一笔的代价。
5. **不可逆操作必须有确认闸门。** 而且每次修改后要重新确认。
6. **找领域不变式当免费校验器。** 一条好不变式 > 一百行防御代码。
7. **写入必须事务化。** 备份 → 写 → 校验 → 回滚，批量操作要么全进要么全不进。
8. **删除用冲销，别物理删。** 数据只增不改，审计线索才完整。
9. **每次人工修正都是一次训练信号。** 写进记忆表，让系统越用越准。
10. **关键词分类不要用单字做子串匹配。** 中文否定（不行/不好）必踩。
11. **优先复用成熟标准格式。** 别自造私有 schema，白捡别人的校验器。

## 十、面试话术模板

### 30 秒版
> "这是一个给个体户用的自然语言记账助手。核心设计是：
> **AI 只负责把口语理解成结构化草稿，正确性由确定性代码保证。**
> 草稿要过硬校验和用户确认才能落账，落账走事务、失败回滚，
> 底层用的 Beancount 复式记账，借贷平衡天然就是一道数据完整性校验。"

### 3 分钟版（建议按这个顺序讲）
1. **矛盾**：AI 一定会错，但账不能错 → 所以把"识别率"和"数据正确性"分开解。
2. **四道关卡**：LLM 抽取 → 确定性校验 → 人工确认 → 事务落账。
3. **一个具体的技术点**：中文金额解析器（三百五→350、12块5毛→12.5），
   全用正则+状态机实现，19 个单测覆盖边界——**因为这种事交给模型必然不稳定**。
4. **一个真实的坑**：确认态最初用子串匹配关键词，用户说"不行"被判成"确认"，
   错账直接落账。修法是显式处理否定 + 改判断顺序 + 补回归测试。
   （讲坑比讲亮点更能证明你真的做过。）
5. **学习机制**：用户每确认一次就把"面粉→存货"写进映射表，越用越准。
6. **诚实的收尾**：识别率还没有真实用户数据量化，这是下一步。

### 可能的追问

**Q: AI 识别错了怎么办？**
> 分两层。识别错了，它会先撞上确定性校验（金额解析不出、科目不在词表里就退回澄清）；
> 侥幸过了校验，还有用户确认这一关。真正的兜底是：**没有任何一条 AI 的输出能不经确认就落账**。

**Q: 为什么不用 LLM 直接生成数据库操作 / SQL？**
> 因为不可复现也不可校验。我让 AI 只填预置的报表模板参数，聚合计算全在 Python 里做
> （`flows/query.py`）。**报表数字错了比报表难看严重得多。**

**Q: 怎么保证 AI 输出格式稳定？**
> 三层：`json_object` 格式约束、Pydantic Schema 强校验（枚举/类型全写死）、
> 解析失败自动剥围栏降级重试。任何一层过不了都进澄清流程，不会崩也不会带脏值往下走。

**Q: 这套东西放到别的领域能用吗？**
> 能，骨架是通用的五步：定义受控词表 → 设计 Schema → 写领域校验器 →
> 加确认闸门 → 接反馈学习。记账里的"借贷平衡"换成设备管理里的"读数范围+巡检项必填"
> 就行，LLM 那部分几乎不用改。

## 十一、本项目的已知短板（主动说出来，比被问出来好）

| 短板 | 现状 | 怎么补 |
|---|---|---|
